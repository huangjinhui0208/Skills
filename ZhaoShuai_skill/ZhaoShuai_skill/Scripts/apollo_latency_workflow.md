# Apollo Latency Workflow

用于：
- 在 Apollo 10.0.0 中打点
- 收集模块执行时间和抖动
- 对异常值进行代码级追踪分析

## 目标
不是只拿到一份时延数据，而是完成以下闭环：
1. 看懂模块内部执行逻辑
2. 明确应该在哪里打点
3. 保证关键路径没有遗漏
4. 收集执行时间和抖动数据
5. 判断异常值是否稳定出现
6. 找出高时延/高抖动模块
7. 建立“异常现象 → 输入输出 → 触发条件 → 关键代码段”的映射

## Step 1：先读代码
回答这些问题：
- 模块主入口函数是什么？
- 主处理链路是什么？
- 哪些代码属于真正的核心执行逻辑？
- 输入数据从哪里进入？
- 输出数据从哪里发出？
- 有哪些子阶段？

输出整理为：
- 模块入口
- 主处理函数
- 关键调用链
- 输入
- 输出
- 可疑耗时段

## Step 2：设计打点方案
打点原则：
- 必须包住完整关键路径
- 不能只打局部辅助逻辑
- 必须至少有一个 total 点
- 必要时补子阶段点

建议至少包含：
- total：整个主处理流程
- input：接收/读取输入
- core：核心计算或处理逻辑
- output：发布/写出输出

检查项：
- 是否有关键代码没被覆盖？
- 是否能从点位名字看出语义？
- 是否能通过这些点回推出完整执行链？

## Step 3：收集数据
采集后，先做基础整理：
- 每个模块的执行时间
- 每个模块的抖动
- 平均值 / P95 / P99 / 最大值
- 异常值位置
- 异常值出现次数
- 异常值是否重复出现

## Step 4：老师式追问
必须先问：
- 这些异常值是否每次都会出现？
- 是周期性出现，还是偶发出现？
- 哪些模块时间延迟更大？
- 哪些模块抖动更多？
- 这些判断有什么数据支撑？
- 这些异常是否和特定输入有关？
- 这些异常是否和代码中的某一段重逻辑有关？

## Step 5：补齐模块输入输出映射
对异常模块，必须补齐：
- 输入数据是什么
- 输出数据是什么
- 输入变化是否影响时延
- 输出前是否存在阻塞、等待或重计算

## Step 6：定位真正触发点
不要只停留在“这个模块慢”。
要继续追到：
- 是哪个子阶段慢
- 是哪段代码真正触发
- 是稳定逻辑耗时，还是偶发外部条件触发
- 是输入规模、锁竞争、等待、循环、IO、调度，还是算法复杂度导致

## 最终输出结构

### 1. 模块执行逻辑
- 入口
- 主流程
- 输入
- 输出

### 2. 打点设计
- 点位名称
- 所在代码段
- 覆盖语义
- 是否覆盖完整关键路径

### 3. 数据现象
- 哪些模块时延高
- 哪些模块抖动大
- 是否稳定复现
- 哪些是异常值

### 4. 原因判断
- 数据依据
- 输入输出关联
- 可疑代码段
- 真正触发代码段

### 5. 建议动作
- 应先验证什么
- 应补什么点
- 应继续追哪段代码
